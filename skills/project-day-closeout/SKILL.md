# 打完收工

让本段工作留下可恢复的成果、准确的主线和明确的接续位置。用户可以只调用这一个入口；目录整理和 Git 存档仍由相邻的辅助技能完成。

## 先确定范围与模式

读取当前项目存在的 AGENTS、其指定的规范、索引和工作主线，以及存在时的 .agents/project-profile.md。只沿现有入口读取受影响资料。若 AGENTS、索引或 profile 缺失，可从 README 和用户当前请求确定最小范围；缺失本身不授权创建新入口、项目规范、索引或 profile，必须说明相应覆盖限制。确认工作目录、当前任务、已有授权与 Git 状态；不跨项目收口。

| 模式 | 何时使用 | 允许的结果 |
|---|---|---|
| full 完整收工 | 用户明确说“打完收工”“今日收工”“保存进度并收口”，或项目已经授权稳定任务结束时完整收工 | 完成责任文件和目录收口后，对本任务归属清楚、通过必要检查的批次做本地提交 |
| readiness_only 只准备 | 其他技能内部转交、仅要求同步状态或准备提交，或没有明确要求完整收工 | 完成相应文档收口并返回 git_readiness，不暂存、不提交 |
| audit 只检查 | 用户要求只读、先检查或先评估 | 读取并报告，不修改文件或 Git |

完整收工请求可包含对本任务稳定成果的常规本地存档，但不撤销仍适用的“不要 Git”“只记录”等限制。项目已有长期本地提交授权时可直接沿用；不把授权扩大到其他任务、远程推送或受保护对象。“明天继续”等只表示接续，不能单凭关键词认定完整收工授权。

模式是给执行者的文字约定，不是已实现的命令行参数。内部调用未说明模式时使用 readiness_only，不能因进入本技能获得提交授权。

## 辅助依赖与调用关系

完整收工依赖同一公开仓库中的 project-directory-closeout 和 project-git-closeout 两个辅助技能。开始时检查相邻技能目录及其 SKILL 文件是否可用；缺少任一依赖时，继续完成不依赖它的主线和责任文件收口，并明确列出受影响阶段，不能报告完整收工已完成。

不得回退到个人源目录、临时安装技能或用未声明的替代实现掩盖依赖缺失。metadata 中的 requires 只是仓库说明，不会自动安装、发现或递归调用技能。目录辅助可以独立运行；Git 辅助独立运行时只接受本次 readiness，不反向启动本技能。

## 一次收工的顺序

1. 确认本段工作。对照已有主线和实际文件，辨明完成、未完成、返工和未知；记录真正影响接续的问题。Git 变更列表不等于本任务文件列表，其他任务文件和未知暂存项先分开。
2. 核对各级索引与目录。完整收工读取并执行[索引对账规则](references/index-reconciliation.md)：按项目登记范围发现索引职责入口，用有效基准、Git 已提交及未提交变化和实际路径确定缺口，同步应更新的当前登记。不能只看本轮脏文件。目录辅助可用时，对具名受影响目录调用 project-directory-closeout，复用本轮发现结果，不重复扫描；不可用时说明目录阶段未覆盖。收工本身不删除或搬移材料。readiness_only 按调用方具名范围执行并说明覆盖，audit 只检查。
3. 同步主线并留好接续。新结果、纠偏、阻塞或下一步变化，直接写回项目既定责任文件；有 OpenSpec 时核对受影响任务及完成依据，不把 Git 提交当验收。接续最少留下当前目标、已做或未做、结果与来源位置、下个具体动作；有未决条件、费用或失败恢复位置时一并保留。不新建第二份 Roadmap 或每轮总结文件。
4. 检查并收掉文档尾巴。核对修改内容、引用、必要验证、原始文件边界，以及本次收口是否又产生遗漏。无实质变化不改日期；验证强度服从实际改动，不为小文案强造测试工程。
5. 形成 Git 准备结果。使用[readiness 参考](references/generic-day-closeout-readiness.md)保留既有字段，并逐批说明精确路径、授权来源、必要验证和待处理项。先完成前面的文档更新，再固定本批检查依据。
6. 按模式完成存档。full 且本批 ready、Git 辅助可用时，调用 project-git-closeout 完成本地暂存与提交，不停在“可以提交”的建议。readiness_only 和 audit 均不暂存或提交。Git 辅助缺失时只返回准备结果并说明 Git 阶段受影响。必需验证缺失、文件还在变化、来源归属不清或授权不足时，只暂缓受影响批次；其余不依赖它的稳定批次可继续。
7. 核对实际结果。检查提交号、提交路径、暂存区和残余变更；说明哪些成果已存档、哪些仍未提交。Git 失败如实记录，不能把 readiness 通过写成提交成功；不要为了把最新提交号写回主线再制造一次循环提交。

## 调用边界与恢复

- 主执行者统一执行一次收工流程。目录辅助只返回本次结果，不反向启动另一轮收工；被调用的 Git 技能缺材料时返回主执行者处理，不递归互调。
- 无 Git 仓库时完成文件和接续收口，明确“尚无 Git 存档”；不自动初始化仓库、配置身份或远程。已有仓库遇身份、锁或并发问题时保留现场，不清空未知暂存、不强删锁、不覆盖其他工作。
- 只提交归属明确的具名文件，保留私密配置、凭据和未接收来源。本技能不执行新的文件删除或搬移动作。已经发生的删除或改名变更，只有另有具体授权且完成资格、恢复依据和必要例外核查，才可交给 Git 辅助纳入提交；条件不足则暂缓这些路径。不执行 reset、clean、历史改写或默认推送。
- full 收工可保存已验证的中间检查点，但必须说明业务未完成部分。必需验证失败的成果不能因“要下班”被标为可提交。
- 本技能在被调用时执行，不常驻、不唤醒电脑、不自动创建或重开定时任务。调度属于独立请求。
- 用户停止时立即停；意外中断后先检查主线、HEAD、暂存和未提交内容，从真实位置继续，不重做已有调查或把未保存说成已保存。无变化时不写重复记录、不做空提交。

## 汇报

用用户或项目约定的语言说明本段工作的位置和结果、主线或目录更新、必要验证、实际 Git 结果、未处理事项及下次入口。项目已有固定格式时沿用；没有项目格式时用简短段落或列表，只有真实阻塞需要决策时才提问。

索引结果逐入口区分：已更新、核对后无需更新、历史保留、未核实或受阻，并说明检查范围与依据。登记范围存在遗漏时只能报告部分收口；准确登记的业务未知不要求在收工时重新完成业务验收。

Git 结果必须区分：已提交、无变化无需提交、仅准备未提交、部分提交、受阻或失败。提供实际提交号或具体未提交原因；文件已写入、Git 已存档和业务已验收分别报告。
