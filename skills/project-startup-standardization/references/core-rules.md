# 通用规则切片

这些是项目没有更具体约定时可选用的判断原则，不是认证标准或固定目录模板。已有项目规则、生态约定和用户授权优先。

## 目录与环境

- 为实际使用的目录说明用途、写入者、保留方式和是否进入版本管理；不为可能的未来需求创建空目录。
- 区分源码、原始输入、工作结果、交付物、缓存、构建输出和历史资料。目录名称本身不证明内容已发布、可删除或可重建。
- 环境信息只记录实际已知的服务、数据和部署目标；不把未知配置、密钥或未部署能力填成事实。

## 名称、身份与版本

- 框架和语言的固定文件名保持原样；其他文件采用项目既有的语言和命名风格。
- 当来源、复用、交付、版本比较或恢复会影响判断时，为重要对象使用稳定标识、revision 或批次号。普通说明文档不必为了形式增加编号。
- 当前规则可以原地维护；历史使用现有版本控制或明确的历史位置保留。不要仅凭 final、latest、new 或日期判断哪个版本有效。
- 同一重要对象的新版本不应悄悄覆盖来源关系；无法判断时保留旧项并标注待核实。

## 索引与来源关系

- 选择一个项目已经能维护的入口，登记重要输入、跨步骤结果、交付物和批次；可以是 README、Markdown 清单、manifest 或已有系统。
- 最小信息通常包括路径、用途或状态、来源或生成过程、当前或历史关系和保留依据。源码可按模块和版本控制管理，不必逐文件登记。
- 大批量同类文件可以由批次清单覆盖；清单应能定位实际路径和输入输出关系，不能只写“目录下全部文件”。
- 不知道来源、状态或消费者时写未知，不能用文件名或日期猜测。

## 写入、历史与清理

- 新建或修改重要产物前，先检查是否已有同职责入口，再决定原地更新、创建新版本或建立新批次。
- 生成后回读实际路径和必要引用；登记失败或验证失败时保留旧当前项，并报告本次未完成。
- 移动、归档或删除前检查已知引用、唯一价值、恢复方式和明确授权。未知对象保持原位，不因缓存、generated 或忽略规则就自动清理。
- 并行工作使用独立工作区或明确的合并责任；不要要求协作者凭记忆维持公共清单。

## 能力边界

文档和索引帮助人和工具理解项目，但不会自动阻止未读取规则的脚本或协作者。自动生成、发布和外部同步只有在项目已经真实接入并验证后才能描述为现有能力。
