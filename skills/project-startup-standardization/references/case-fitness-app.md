# 案例：从想法和 HTML 演示开始的健身应用

这是教学案例，不要求用户一次性想清楚产品，也不要求第一轮实现完整后台。

## 起点

用户只有一句想法：“做一个给自己用的健身管理应用。”之后通过对话和 AI 生成了一个 HTML 界面，界面里可能有训练计划、今日打卡和进度卡片。用户后来又想到要发布到互联网，可能需要用户数量、功能使用情况、购买记录和 AI 教练，但这些不一定在第一轮已经确认。

## 第一次标准化

先把当前材料整理成“现在已经有的东西”和“还没有确认的东西”。经用户授权后，可建立最小可工作的结构：

    fitness-app/
    ├─ README.md                 # 当前工作入口
    ├─ docs/
    │  ├─ 项目规范.md            # 仅在需要时建立
    │  ├─ 当前索引.md            # 仅登记重要材料
    │  └─ 冲突与修订记录.md      # 有实际冲突或修订时使用
    └─ demo/
       └─ fitness-demo.html

这一轮至少说明：HTML 是演示材料，不是生产前端；demo 目录放演示；README 是当前入口；尚未确认的后台、账号、支付、统计、AI 教练不创建空目录，也不伪装成已规划完成。

## 后续材料如何进入

当用户继续讨论“要发布到互联网”，再补充部署目标、用户数据边界和运行环境；当用户确认“需要知道下载量和常用功能”，才补充事件记录与统计规则；当用户确认“需要购买”，才补充商品、订单、支付状态和敏感数据边界；当用户确认“接入 AI 教练”，才补充模型调用、提示词、会话记录和费用控制规则。每次只补充受当前材料影响的规则，不重新初始化整个项目。

## 前后矛盾的处理

第一轮写着“暂不保存训练对话”，第二轮用户确认“保存 AI 教练总结供下次查看”，这不是静默覆盖。项目可在已有的修订记录中保存旧规则、新决定、原因、影响范围和处理结果；当前规范只保留已采用的新规则，受影响的入口、文件索引、隐私说明和后续任务再按实际范围同步更新。

## 本案例的边界

技能负责把材料变成可执行的项目秩序和持续修订过程；它不替用户决定产品价值，也不因为看到了 HTML 就自行实现后台、支付或 AI 服务。
